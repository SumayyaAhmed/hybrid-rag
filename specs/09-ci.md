# 09 — CI pipeline (GitHub Actions)

Status: **implemented** (2026-11-04). 24 unit + 14 integration tests.

## Goal
On every push to `main` and every pull request, GitHub checks automatically that the code is clean, the logic
works, the database image builds, and the migrations and SQL queries work against real Postgres.

## Ground rule: CI uses no API keys
Voyage and Gemini are never called in CI:
- keys would have to be stored as GitHub Secrets;
- Voyage is limited to 3 req/min and Gemini's free tier is used up quickly;
- results would vary from run to run, and tests should be deterministic.

So `embed()` and `rerank()` are replaced in tests with **fakes** (pytest `monkeypatch`): fixed vectors and fixed scores.
That tests *our* code (SQL, fusion, filtering, prompt building), not the hosted models. Model quality is measured by
the eval (`make eval`, locally). The eval is not part of CI.

## Workflow: `.github/workflows/ci.yml`
Two jobs run in parallel; either one failing marks the commit ❌.

### Job 1 `lint-and-unit` (~30 s, no database)
1. checkout → install uv → `uv sync --frozen`
2. `uv run ruff check .`: linting (unused imports, undefined names, syntax errors)
3. `uv run pytest -m "not db"`: unit tests

### Job 2 `database` (~3 min)
1. checkout → install uv → `uv sync --frozen`
2. `docker compose up -d --build --wait db`: builds `db/Dockerfile` (catches a broken pg_textsearch build)
3. `uv run pytest -m db`: integration tests against a separate `rag_test` database
4. `docker compose build app`: the app image (spec 08) still builds

Total: 14 existing + 10 new unit tests + 14 integration tests.

**Every BM25 test runs twice, once with `enable_indexscan = off`.** On a tiny table with statistics, Postgres prefers
Seq Scan + Sort over the bm25 index. The seq scan scores *every* row (0 for non-matching ones), while the index returns
only matches. `rag_test` has no statistics, so without forcing it the seq-scan path was never tested. A deliberate
removal of the `score > 0` filter in `keyword.py` passed all tests until this was added.

`tests/helpers.py` builds `Hit` objects for unit tests; `tests/conftest.py` creates + migrates `rag_test` in
`pytest_sessionstart` (before `rag.db` opens its pool) and holds the fakes (`FakeEmbed`, `fake_embedding`,
`fake_count_tokens`) plus the session fixture `ingested`. If Postgres isn't running, db tests are skipped, not failed.

## Tooling changes
- `ruff` added as dev dependency; config in `pyproject.toml`: `line-length = 150`, rules `E`, `F`, `W` (pycodestyle + pyflakes).
  Ruff 0.17's broader default set mostly flagged style (35× implicit string concat in sample data). The one bug-like finding
  (B023, loop variable in a lambda in `clients.embed`) is a false positive: the lambda is called inside the same iteration.
  `scripts/make_sample_data.py` ignores E501 (long sample strings).
- `pytest` marker `db` registered in `pyproject.toml`.
- Makefile: `lint`, `test` (unit only), `test-db`, `ci` (= lint + test + test-db + app image build, the same as GitHub runs).
- `db/migrations/env.py`: honours `config.attributes["database_url"]`, so tests can migrate scratch databases.
- `docker-compose.yml`: `app` service's `.env` is `required: false` (CI has none and only builds the image).

## Not in CI (and why)
- **Eval**: needs keys + ~20 min at 3 req/min; it's a quality measurement, not a pass/fail gate. Run `make eval` locally.
- **Real Voyage/Gemini calls**: see ground rule.
- **Deploy / image publishing**: nothing is deployed.
